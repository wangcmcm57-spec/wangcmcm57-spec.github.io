## Context（为什么做这件事）

目标：为王帅搭建一个**面向古茗 AI 团队**的个人网站，作为投递岗位时的"立体化简历"。

## 视觉基调（B 为主融合 A）✅ 已确认：复古纸感

整体：**克制、留白、有质感**，像工作笔记而非作品集。用户已从 4 套视觉小样（复古纸感 / 现代极简 / 暗夜工作站 / 编辑杂志风）中确认选择「复古纸感」。

| 维度 | 方案 |
|---|---|
| 背景 | 暖白纸感 `#FAF8F3`，营造"笔记本/工作台"感 |
| 主文字 | 近黑 `#1A1A1A` |
| 强调色 | 墨绿 `#2F4F3E`（呼应生鲜零售背景，且有质感，不花哨） |
| 辅助色 | 暖灰 `#8A8278`（用于次要信息、分隔线、状态标签） |
| 标题字体 | 衬线（系统宋体 / Georgia），增加思考感 |
| 正文字体 | 系统无衬线（PingFang / -apple-system） |
| 标签 / 状态 | 等宽字体（mono），呼应"工作站"调性 |
| 动效 | 仅微动（hover、锚点平滑滚动），不堆砌 |
| 布局 | 单栏为主、宽留白、细分隔线（`border-top` 营造章节呼吸） |

### 3. Case Study 1：订购专家 Agent `projects/ordering-agent.html`

按用户方案的结构（这是网站辨识度核心）：

- **01｜问题**：订购规则散落在 PRD、原型、研发文档、业务确认记录、历史需求、线上问题。导致"业务问一句 → 找产品 → 产品找文档 → 找不到 → 研发反复确认"。
- **02｜我重新理解这个问题**：不是"做一个知识库"，而是**如何让组织里的业务事实变得可查询、可验证、可追溯**。
- **03｜重新设计工作方式**：业务提问题 → AI 理解 → 检索业务事实 → 给出证据 → 判断是否足够 →（足够）输出结论 /（不足）人工确认 → 沉淀新知识。配流程图（纯 HTML/CSS 画的纵向流程）。
- **04｜AI 在这里到底做什么**：AI 负责理解、检索、组织、解释；业务规则仍由系统和专业人员确认。**证据门控**：知识库未覆盖或口径冲突时不得编造结论，必须进入产品/研发确认。设计"提需求"和"查规则/问问题"两类工作流。
- **05｜结果与价值**：降低多角色反复解释规则的成本；把资深产品经验沉淀为可复用、可追溯、可持续更新的团队资产；输出边界追问、BRD 草稿、规则依据、问题记录草稿、待确认清单。
- 侧栏 `Resume View` 切换：点击切到简历式摘要（负责什么 / 做了什么 / 结果是什么）。

### 4. Case Study 2：AI 新品推荐 `projects/ai-new-product.html`

同结构：
- **01｜问题**：新品开发主要依赖采购经验、供应商信息、市场观察，缺少把门店销售、客群画像、品类机会、竞品价格、趋势证据、毛利风险串起来的数据化决策工具。
- **02｜重新理解**：不是"AI 替采购选品"，而是**帮采购从纯经验开品升级为"数据证据 + 人工判断"**。
- **03｜重新设计**：把采购选品拆为 内部机会识别 → 外部竞品/趋势验证 → 候选标准化 → 价格与毛利可行性 → 风险门禁 → 推荐优先级 → 采购反馈。华东/上海试点工作台。
- **04｜AI 作用**：定义离线算法 / 后端 / Agent / 前端边界——算法产出推荐结果和证据快照，Agent 解释结构化结果，前端展示并收集反馈；**不让大模型直接扫描明细数据、实时重算算法或替采购拍板**。
- **05｜结果与价值**：采购决策方式升级为"数据证据 + 人工判断"；沉淀采购反馈闭环；为试点复盘、算法调优、规模化推广打基础。
- 同样配 `Resume View` 切换。

### 5. How I Work `how-i-work.html`

用户方案里的 9 步工作法，纵向流程呈现，每步一句话 + 一句"为什么这一步重要"：

01 进入真实业务 → 02 找到值得解决的问题 → 03 拆解现有工作方式 → 04 判断哪些可以删掉/自动化/AI 化 → 05 做最小可运行验证 → 06 找真实用户试 → 07 观察失败 → 08 复盘价值 → 09 沉淀成可复用能力。

页尾一句话点题：这套方法对应古茗 JD 的"问题研究 → 方案验证 → 采用复盘 → 方法沉淀"。
